1. Purpose, scope and interpretation rules
This document is the consolidated source of truth for the benchmarks performed during memoriX development. It replaces scattered notes and explicitly separates audited results, reported historical results and invalid executions.
Central conclusion: memoriX strongly improves internal tasks when relevant memories are available, operates stably through MCP, preserves 92% of references in BFCL-derived blind curation, produces 72% correct answers in that condition, and was validated up to 5,000 atomic memories with lossless manual extension.
Percentages from different protocols are never merged as if they measured the same quantity.
BFCL campaigns are local and BFCL-derived; they are not official leaderboard scores.
The Galileo campaign uses a local completion/tool-call proxy, not the official Galileo score.
Robustness and capacity results come from targeted diagnostic protocols.
Invalidated executions are documented only for reproducibility and excluded from conclusions.

11. Real todo-list integration validation
A real SDLC cycle in OpenCode created a todo-list application, produced a PRD, plans, files and five passing tests. The observed memory behavior matches the memoriX contract.
Interactions and tool calls are logged in short_term/events.jsonl (65 observed events).
The “Todo list app v1 built and validated” milestone is recorded in the cold project archive.
memory_store creates candidate_fc33665bb9094b278e51fe11867bc8a6 in pending_review.
The candidate is not retrievable before validation.
After user approval, memory_candidate_validate writes the memory to Titan.
memory_retrieve retrieves the architecture as memory_35d2e874d38f4759aff502601d0bb1c4.
This test also identifies an improvement to formalize: OpenCode should automatically propose a candidate at the end of a validated cycle, but must never validate it automatically. Two nearly identical project_archive_record calls were observed and could be deduplicated.
12. Cross-benchmark synthesis
Question
Evidence-based answer
Does OpenCode–MCP–Python transport work?
Yes: Galileo, BFCL and the todo-list validate transport and calls.
Is validated storage persistent?
Yes: persistence after restart up to 5,100 active memories.
Can the system retrieve explicitly stored information?
Yes: 25/25 in the oracle pilot and 36/36 distinct facts.
Does the system always choose the right memories autonomously?
No: 23/25 blind corpus; 22/25 retrieval; 18/25 answers.
What is the main bottleneck?
Protocol-dependent: curation and generation in blind evaluation, then retrieval in difficult robustness cases.
Does memory saturate safely?
Yes: validation blocked, candidate pending, no silent overwrite.
Does EXPAND automatically resize Titan?
No: dry-run recommendation; manual extension validated.
Are topic blocks reliable?
With tags: 47/48 exact. Without tags: substantial fragmentation.

14. Limitations, conclusions and future work
14.1 Supported conclusions
In the internal protocol, OpenCode + memoriX succeeds on 58/58 valid tasks versus 38/58 for the baseline, with no paired loss.
The memory pipeline is technically stable: storage, validation, restart and retrieval work on CPU.
When the correct information is explicitly selected, memoriX reaches 25/25 in the BFCL-derived oracle pilot.
Under blind curation, the system preserves 23/25 references, retrieves 22/25 and produces 18/25 correct answers.
In the diagnostic robustness benchmark, the corpus contains 29/30 references, retrieval finds 22/30 and 20/30 answers are correct.
Capacity was validated at least to 5,000 atomic memories and manually extended to 5,100 active memories without loss.
Topic blocks are highly reliable with canonical tags but fragmented without guidance.
14.2 Unsupported conclusions
memoriX officially scores 100% on BFCL.
The absolute maximum capacity is 5,000 memories.
EXPAND automatically resizes Titan.
Internal results prove general superiority across all agents and datasets.
The Galileo proxy result is an official leaderboard score.
14.3 Priority future work
Formalize automatic candidate creation at the end of a validated OpenCode cycle while keeping human validation.
Deduplicate identical project_archive_record writes.
Improve retrieval for weak formulations or lexically distant memories.
Require final-answer generation to use retrieved evidence before returning UNKNOWN.
Make topic blocks more semantic and use tags as an explicit policy.
Add controlled and auditable capacity extension, potentially triggered after an EXPAND recommendation.
Measure RAM and optimize latency beyond 2,500–5,000 memories.
