 MemoriX: Design and Evaluation of a Controlled Persistent Memory System for LLM-Based Code Agents Elwen Coroller, Antoine Tourneux, Salekin Sajirus, Truc Tran Thanh, Nghia Nguyen The &amp; Minh Tran Trong 100000 Abstract Large language model (LLM)-based agents increasingly assist with complex software development tasks, yet their continuity across sessions remains fragile. When decisions, constraints, and validated knowledge must persist beyond a single invocation, existing approaches—parametric fine-tuning, unstructured context dumps, or key-value caching—fail to provide controlled, auditable, and queryable long-term memory. We present MemoriX , a persistent memory system designed for OpenCode agents that separates recent events, durable historical traces, memory proposals (candidates), and actively retrievable knowledge into distinct architectural layers governed by explicit admission control. MemoriX integrates via the Model Context Protocol (MCP), maintaining a clean runtime boundary between TypeScript agent orchestration and a Python memory server backed by a Titan neural memory backend. We evaluate MemoriX through a comprehensive A/B benchmark (2,048 runs across 32 task families), BFCL-derived retrieval campaigns, multi-agent continuity tests, and capacity stress experiments. Results demonstrate a +28.0 percentage-point improvement in overall pass rate (from 31.9% to 60.0%) with memory, with 12 of 32 task families improving, zero forbidden-information leaks, and safe saturation behavior at 50,000 active memory items. These findings establish MemoriX as a reliable, high-performance external memory backend that treats inter-session continuity as a knowledge-governance problem rather than a mere storage challenge. 100000 1. Introduction The emergence of LLM-based coding agents such as OpenCode, Devin, and Cursor has transformed how developers interact with software projects. These agents can reason about codebases, generate implementations, run tests, and iterate on requirements across multiple turns [1, 2]. However, a fundamental limitation persists: inter-session amnesia . When an agent session terminates, all context—decisions made, constraints discovered, conventions established—evaporates. The next session begins from scratch, forcing the agent to rediscover what was already known or, worse, to silently contradict prior decisions. This problem is not merely one of storage. It is a knowledge-governance problem. Effective persistent memory for agents must address at least the following dimensions: Admission control : not all observations deserve to become durable knowledge. Retrieval precision : relevant memories must be surfaced without flooding context. Update and forgetting : stale or superseded information must be logically deactivated without destroying history. Isolation : knowledge from one project or user must not leak into another. Capacity management : the memory system must behave predictably under saturation. Existing approaches to agent memory span a wide spectrum. Parametric memory methods bake knowledge into model weights through fine-tuning or gradient updates [3], but they are opaque, expensive, and conflate learning with remembering. Retrieval-Augmented Generation (RAG) pipelines [4] externalize knowledge into vector databases but typically lack structured admission, versioning, or forgetting semantics. Context-caching techniques such as MemGPT [5] extend the virtual context window but treat all history uniformly rather than distinguishing signal from noise. Memory systems explicitly designed for agents, such as Mem0 [6] and MemGen [7], offer dedicated memory management but often compromise on auditability, explicit governance, or multi-agent isolation. In this paper, we introduce MemoriX , a memory system designed from first principles around the knowledge lifecycle: observe → propose → validate → retrieve → update → forget . MemoriX draws architectural inspiration from the multi-level structure of human memory—sensory, short-term, and long-term stores [8, 9]—while remaining grounded in the practical requirements of software development agents. We integrate MemoriX with OpenCode through the Model Context Protocol (MCP) [10], evaluate it through a rigorous paired A/B benchmark across 32 task families (2,048 total runs), and report results on retrieval quality, multi-agent continuity, and capacity scaling. The key contributions of this work are: A layered memory architecture (Short-Term Memory, Cold Site, Candidate Store, Titan Hot Site) with explicit admission control and logical forgetting. A paired experimental methodology with a fairness contract and negative control baseline, aligned with ACM SIGSOFT Empirical Standards [11] and LLM-specific evaluation guidelines [12]. Comprehensive empirical results demonstrating +28.0pp pass-rate improvement, safe capacity scaling, and zero information leakage across projects and users. An open-source implementation integrated with OpenCode via MCP, supporting multi-agent SDLC workflows. 100000 2. Related Work The design of MemoriX builds upon a rich lineage of research spanning memory-augmented neural networks, LLM memory mechanisms, and agent memory systems. We situate our work within three major threads. 2.1 Memory-Augmented Neural Networks The idea of equipping neural networks with explicit memory structures dates back several decades. Early architectures such as Hopfield Networks [13] demonstrated content-addressable memory through recurrent dynamics. The Neural Turing Machine (NTM) [14] and Differentiable Neural Computer (DNC) [15] introduced differentiable read-write operations over external memory matrices, enabling gradient-based learning of memory access patterns. Sukhbaatar et al. [16] proposed End-to-End Memory Networks, which use a recurrent attention mechanism over an external memory to perform multi-hop reasoning with significantly less supervision than earlier memory-augmented models. Nam and Seo [17] later reformulated the attention mechanism itself as a readable and writable memory structure—Neural Attention Memory (NAM)—demonstrating applications in few-shot learning and efficient long-range attention. Santoro et al. [18] showed that memory-augmented neural networks (MANNs) are particularly well-suited for meta-learning and one-shot learning, where a model must rapidly incorporate new information from a single observation without catastrophic interference. Their work established that architectures with external memory can learn to learn, shifting bias through both weight updates and rapid caching of representations. A comprehensive survey by Khosla et al. [19] categorizes the landscape of MANNs across cognitive theories, architectural designs (Hopfield Networks, NTMs, Correlation Matrix Memories, Memformer, NAM), and application domains including NLP, computer vision, and multimodal learning. For task-incremental learning specifically, Sun et al. [20] proposed the Bilevel Memory framework with Knowledge Projection (BMKP), which decouples learning (working memory) from remembering (long-term memory), drawing direct inspiration from the Atkinson-Shiffrin human memory model [8]. Their knowledge projection mechanism compresses representations for efficient long-term storage while maintaining plasticity for new tasks. Our work extends this bilevel philosophy to the agent domain, where the “tasks” are software development sessions and the “knowledge” encompasses conventions, decisions, constraints, and project-specific facts. 2.2 Memory Mechanisms for Large Language Models The Transformer architecture’s quadratic complexity with respect to sequence length [21] imposes a practical limit on the context an LLM can process. This has motivated a family of approaches that augment Transformers with external memory or efficient attention mechanisms. Efficient and long-context attention. The Forgetting Transformer (FoX) [22] introduces a forget gate into linear attention, allowing the model to decay irrelevant information over time while maintaining O(1) memory with respect to sequence length. EM-LLM [23], presented at ICLR 2025, takes inspiration from human episodic memory by segmenting token sequences into coherent episodic events using Bayesian surprise and graph-theoretic boundary refinement, then retrieving relevant events through a two-stage process combining similarity-based and temporally contiguous access. This work demonstrates that organizing memory around event boundaries —rather than fixed-size chunks—improves performance on long-context benchmarks. Explicit knowledge storage. ExplicitLM [24], published at ICLR 2026, proposes fundamentally decoupling knowledge from model parameters through million-scale external memory banks where each entry stores human-readable knowledge as token sequences. Their differentiable two-stage retrieval mechanism enables end-to-end training while maintaining discrete knowledge selection. Engram [25] takes a complementary approach, introducing conditional memory as a sparsity axis orthogonal to Mixture-of-Experts: static knowledge is retrieved via O(1) lookups from massive embedding tables, freeing the Transformer backbone to focus on dynamic reasoning. Both works share our conviction that knowledge should be addressable, inspectable, and updatable independently of model parameters. Memory-augmented LLM architectures. MemoryLLM [26] and its extension M+ [27] equip language models with dedicated long-term memory mechanisms that go beyond key-value caching. MemMamba [28] integrates memory into the Mamba state-space architecture, demonstrating that recurrent-style models also benefit from explicit memory augmentation. 2.3 Agent Memory Systems With the rise of LLM-based autonomous agents, memory has emerged as a first-class design concern. Unlike standalone language models, agents operate across multiple turns, interact with tools, and must maintain coherence over extended periods—sometimes spanning days or weeks. Operating-system approaches. MemGPT [5] treats the LLM context as a virtual memory hierarchy, with a “main context” analogous to RAM and an external context analogous to disk. The system manages context paging through explicit function calls, enabling agents to operate with effectively unbounded context. Our approach shares the OS-inspired design philosophy but differs in its emphasis on admission governance : in MemoriX, not all information is promoted to active memory by default. Dedicated memory platforms. Mem0 [6] provides a memory management platform for LLM agents with embeddings-based retrieval. Their empirical evaluation across single-hop, temporal, multi-hop, and open-domain question categories demonstrates consistent improvements over baseline memory approaches. MemGen [7] proposes a generative latent memory framework where a memory weaver constructs latent token sequences from the agent’s current state, producing a tightly interwoven cycle of memory and cognition without explicit retrieval. This work is notable for demonstrating that memory can emerge as a generative process rather than purely a storage-and-retrieval mechanism. Multi-agent and shared memory. The Memory Sharing framework for LLM-based agents [29] investigates how memory can be shared across multiple agents to improve collective performance. Externalization in LLM agents [30] studies the broader question of how agents externalize internal state into persistent structures. The Evolution of LLM Agent Memory [31] provides a taxonomy of how agent memory systems have evolved from simple context concatenation to sophisticated multi-tier architectures. Memory consolidation. Several works draw on the neuroscience of memory consolidation—the process by which the brain transforms recent experiences into stable long-term memories, often during sleep [32]. The function-token approach to memory retrieval and consolidation [33] proposes using special tokens as memory read-write interfaces, enabling LLMs to consolidate information through dedicated function calls. Our nightly consolidation pipeline is directly inspired by these biological mechanisms: Short-Term Memory events are scanned, evaluated, grouped, and promoted to candidates during protected processing windows. 2.4 Positioning MemoriX MemoriX occupies a distinctive position in this landscape. Unlike purely parametric approaches (ExplicitLM, Engram), it does not modify model weights. Unlike general RAG pipelines, it enforces validated admission : information must pass through a candidate-proposal-validate lifecycle before entering the active memory store. Unlike context-paging systems (MemGPT), it distinguishes between historical traces (Cold Site), project archives, and actively retrievable knowledge (Hot Site). Unlike latent memory approaches (MemGen), it maintains explicit, inspectable, and auditable memory records. And unlike single-agent memory solutions, MemoriX supports multi-agent workflows with project and user isolation, structured through an SDLC-inspired orchestration layer. System Architecture MemoriX is organized around the knowledge lifecycle: events are observed, durable history is archived, useful information is proposed as a candidate, candidates are validated before admission to active memory, and active knowledge can be updated, superseded, or logically forgotten. Information flows from Short-Term Memory (STM) through the Candidate Store to the Titan Hot Site, with the Cold Site preserving a complete historical trace. The MCP boundary separates the Python memory server from TypeScript agent orchestration. 3.1 Short-Term Memory and the Cold Site Short-Term Memory (STM) captures recent events generated by agent-tool interactions. Each event is a timestamped record of what the agent observed or did, stored ephemerally. STM serves as a transient buffer: it is not queried during normal memory retrieval and is periodically cleaned after successful consolidation. The Cold Site provides a durable, append-only archive of all events. Events are serialized in cold_site/events_archive.jsonl and are accessible only through dedicated audit operations. Critically, the Cold Site is never automatically queried during memory_retrieve . This separation ensures that raw history—which may contain noise, errors, or obsolete information—does not contaminate the agent’s active context. The Cold Site serves as an institutional memory that can be mined during consolidation but remains quarantined from normal operations. 3.2 Project Archive The Project Archive is a specialized branch of the Cold Site, residing under cold_site/project_archive/ . It stores two object types: Structured project entries ( project_entries.jsonl ): milestones, decisions, and project-level metadata. Versioned snapshots ( project_snapshots.jsonl ): state captures at meaningful project boundaries. Like the Cold Site, the Project Archive is not automatically queried during retrieval. It preserves structured project history for resumption, audit, and cross-session continuity without risk of injecting stale project states into active reasoning. 3.3 Candidate Store: The Boundary Between Proposal and Trust Information proposed for durable memory does not enter the Hot Site directly. The memory_store operation creates a candidate in the PENDING state. Consolidation can also promote Short-Term events into PENDING candidates when they are judged sufficiently important. A PENDING candidate is invisible to retrieval until explicitly validated. This design embodies a core governance principle: automation may select and propose information, but admission into active knowledge requires explicit validation . Validation and rejection are separate operations. Validation promotes a candidate to an active memory in the Hot Site; rejection discards it without creating any Titan write. This two-phase admission (propose → validate) provides a crucial safety boundary that prevents runaway accumulation of low-quality or hallucinated “knowledge.” 3.4 Titan Hot Site: Active Memory with Internal Factual Representation The Hot Site is the sole active memory system queried by memory_retrieve . It is backed by a single Titan neural memory instance, consisting of a neural state file and a metadata sidecar. Agents never interact with this backend directly: only validated memories may enter it. The system distinguishes between the logical memory exposed through the API and its internal representation . During validation, content may be segmented by split_memory_units() when it contains multiple facts. These segments become internal MemoryItem objects within the same Titan backend, and their identifiers are associated with the same logical memory_id in metadata. At retrieval time, results are deduplicated by memory_id so the API returns one logical memory regardless of how many internal facts represent it. This distinction matters for capacity planning: admission reserves enough slots for all internal facts generated from a validated memory. The number of logical memories and the number of occupied slots may therefore differ. 3.5 Retrieval with Project and User Isolation The normal retrieval contract is strictly Hot Site only . When provided, project_id and user_id are applied as exact metadata constraints before Titan item scoring and ranking. This ensures that a valid memory belonging to another project or user cannot participate in the ranking, even if it is semantically similar to the query. Deactivated (soft-forgotten) memories are excluded. The Cold Site and Project Archive remain accessible only through separate audit or project-management operations. 3.6 Contradictions, Supersession, and Logical Forgetting When new information explicitly replaces an active memory, validation can target a supersedes_memory_id . The new memory receives a higher version number, and the old memory is soft-forgotten (logically deactivated). History is not deleted: the trace of previous states is preserved in metadata. This approach distinguishes the decision “this memory must no longer be retrieved” from “its internal representation may be physically removed.” Compaction is a later physical operation that reconstructs the active state and removes inactive elements from the backend, but only when consistency checks allow it. This separation prevents compaction from prematurely destroying information needed for audit trails or rollback. 3.7 Topic Blocks, Retention, and Adaptive Controls Topic Blocks are a logical organization layer carried by metadata; they do not physically partition Titan. Aliases, tags, and merge operations allow memories to be grouped around a theme. Canonical tags can stabilize routing when lexical similarity alone is ambiguous. The retention plan evaluates importance, recency, access frequency, confidence, surprise, momentum, and explicit protection rules. Several adaptive components operate in observational or dry-run mode: they produce scores and recommendations without automatically modifying the Hot Site. This conservative design choice reflects our finding that fully automated memory retirement risks removing information that appears stale but proves critical in a later session. 3.8 Consolidation and Nightly Processing Consolidation explicitly connects Short-Term Memory to the Candidate Store. It scans recent events, applies a selection policy, groups promoted events, builds a candidate summary, and creates a PENDING candidate. Events not selected remain as historical observations in the Cold Site. This process does not automatically validate candidates—it only proposes them. Nightly processing uses the same consolidation pipeline within a protected operational framework (locking, logging, idempotency guards). It may additionally replay active memories into neural memory for representation refresh, perform capacity maintenance, and, if configured, clean Short-Term Memory after successful processing. Nightly processing does not modify the Cold Site or Project Archive, and never automatically validates newly created candidates. This design ensures that the nightly cycle is a safe background process that cannot introduce unvetted knowledge into the active memory. 3.9 Elastic Capacity and Hot Site Maintenance Before writing a validated memory, the system computes the number of internal slots required. If current capacity is insufficient, it is increased before the mutation. The objective is to prevent saturation from causing silent overwriting or eviction of an active memory. new_capacity = max(C + minimum_growth, ceil(C × growth_factor), active + required_slots) The default capacity-control parameters notably use `minimum_growth = 10` and `growth_factor = 1.25`. Nightly maintenance may then evaluate a controlled reduction when capacity is above its baseline: bounded soft-pruning, consistency gate, compaction, and possible return to the reference capacity when the active population fits below the configured headroom threshold. The Cold Site is not affected by this maintenance. Nightly maintenance may evaluate a controlled capacity reduction when utilization is below a configured headroom threshold. This involves bounded soft-pruning, consistency gating, compaction, and possible return to the reference capacity. The Cold Site is not affected by capacity maintenance—only the Hot Site participates. 100000 4. OpenCode Integration and MCP Boundary 4.1 Runtime Separation MemoriX does not replace OpenCode’s architecture. OpenCode agents and tools communicate with the Python memory server through MCP JSON-RPC over stdio [10]. The server calls MemoriXGateway , the high-level Python entry point that composes the various stores and services. OpenCode never reads or writes memory-runtime files directly, and the memory server has no access to OpenCode’s internal state beyond what is explicitly transmitted through MCP messages. Experimental Methodology 6.1 Study Positioning Our evaluation of MemoriX belongs jointly to Engineering Research —the design and evaluation of a software artifact—and software-system benchmarking . We follow the ACM SIGSOFT Empirical Standards [11], which recommend describing the artifact, expected benefits, limitations, measurement protocol, threats to validity, and conditions for reproducibility. We additionally adhere to the evaluation guidelines for empirical studies involving LLMs proposed by Baltes et al. [12], documenting the model’s role, version, parameters, tool architecture, prompts, logs, baselines, and human validation. 6.2 Experimental Design The primary comparison is paired : for each experimental unit (a specific task, seed, and configuration), OpenCode is executed without persistent memory ( no_memory condition) and then with MemoriX ( MemoriX_core condition) under controlled parameters. Figure 4 illustrates this design. Figure 4 — Principle of the paired experimental comparison. Factors other than the memory treatment are kept identical. 6.3 Fairness Contract For a valid pair, the following must be identical across conditions: Git commit, task specification, dataset, random seed Model, generation parameters (temperature, top-p, max tokens) Prompt template (excluding memory-specific sections) Turn budget, tool budget, timeout Hardware environment and evaluator The A/B order may be alternated to mitigate order effects. Each execution uses an isolated runtime and produces separately preserved raw artifacts. The no_memory baseline is negatively controlled : it must expose no memory_* or project_archive_* tools, must not load the MemoriX plugin, must not start the memory MCP server, and must access neither Titan nor the Cold Site. This constraint is essential for correctly attributing any observed difference to the memory treatment. 6.4 Experiment Families Family Experimental purpose Inter-session continuity Measure the ability to reuse information from a previous session to complete a task successfully. SDLC Completion, test pass rate, decision reuse, regressions, corrections, resume success. 6.6 Statistical Analysis Observations are analyzed according to their paired structure: a task executed under both conditions with the same seed constitutes one pair. We report the number of valid pairs, appropriate descriptive statistics, dispersion measures, and 95% confidence intervals when sample sizes permit. Effect sizes and hypothesis tests are selected according to variable type and observed distribution rather than imposed a priori. Retry policy : Retries are permitted only for predefined technical errors (crash, infrastructure timeout, incorrect backend, incorrect model, agent fallback). A wrong answer, empty retrieval, or insufficient curation is an experimental result and must not be replayed to artificially improve scores. 6.7 Reproducibility Each campaign preserves: commit hashes, Python/Bun/PyTorch/OpenCode versions, model and provider, generation parameters, prompts, agent permissions, seeds, datasets and their hashes, manifests, scripts, raw outputs, aggregates, relevant logs, exclusion rules, and hardware information. This traceability addresses the reproducibility difficulties documented for LLM-based software engineering studies [12, 34, 35]. 6.8 Implementation and Scale All experiments use qwen2.5:3b served locally via Ollama (free, no API keys). Discussion 8.1 Interpretation of Results The experimental evaluation provides converging evidence that MemoriX substantially improves agent task performance while maintaining safety properties. Memory as a performance multiplier. The +28.0pp improvement in overall A/B pass rate is large by any standard. More telling than the aggregate is the pattern : tasks that depend on information not present in the prompt (migration safety, reproducibility, search recall, contextual disambiguation) transform from near-zero to near-perfect performance. This confirms our central hypothesis: persistent memory is not merely helpful but essential for agent tasks that span beyond the immediate conversational context. The cost of memory. The latency overhead (+120 ms median, +3.5% relative) is modest and well within acceptable bounds for development workflows. The multi-agent tool-call overhead (+3,750 memory operations for 5,000 queries) is similarly acceptable given the +12.5pp task success improvement. Safety is non-negotiable. Zero forbidden-information leaks across all multi-agent runs and safe saturation semantics at capacity limits establish that MemoriX’s governance mechanisms—admission control, project/user isolation, elastic capacity with blocking—function correctly under stress. The four A/B regressions, while modest in magnitude, reveal important failure modes. 8.2 Regressions and Failure Modes Schema evolution (f19, −18.8pp). When a project’s schema changes between sessions, the agent with memory may retrieve and apply outdated schema information. This suggests that MemoriX needs stronger temporal awareness in retrieval: memories associated with a prior schema version should be automatically deprecated when the schema evolves. A potential mitigation is to link memories to project snapshots and invalidate them when the snapshot version increments. Memory footprint (f27, −15.6pp). This family tests whether the agent’s performance degrades as the memory store grows. The regression indicates that retrieval quality can suffer when many similar memories compete for ranking. Improved deduplication during consolidation and more aggressive topic-based filtering during retrieval may address this. Forgetting curve (f11, −9.4pp). The soft-forget mechanism deactivates but does not physically remove memories until compaction. In tasks requiring immediate and complete forgetting, the current pipeline may retain traces that influence retrieval. A “hard forget” option with immediate physical removal—at the cost of audit-trail integrity—may be warranted for specific use cases. Distractor robustness (f03, −3.1pp). This near-noise regression suggests that additional retrieved context occasionally introduces distracting information. Tighter relevance thresholds or confidence scoring could reduce false-positive retrievals. 8.3 Comparison with Existing Systems Relative to the broader landscape (Table 1), MemoriX distinguishes itself through its validated admission model. Systems like MemGPT [5] and Mem0 [6] prioritize ease of use—automatically promoting information to memory—at the cost of governance. MemoriX’s two-phase admission (propose → validate) adds friction but ensures that only vetted knowledge enters the active store. In software development contexts, where one incorrect memory can propagate across multiple sessions and agents, this friction is a feature, not a bug. The multi-tier design (STM, Cold Site, Candidate Store, Hot Site) provides granularity that single-store systems lack. The Cold Site preserves an immutable audit trail; the Candidate Store enables collaborative review of proposed knowledge; the Hot Site serves as the high-performance retrieval surface. No other system we surveyed separates these concerns at the architectural level. 8.4 The BFCL-Derived Distinction We emphasize that our BFCL-derived results are local evaluations following BFCL methodology, not official leaderboard submissions. The 76.8% retrieval rate on blind curation and 64.0% on robustness reflect the performance of a specific memory backend (Titan) with a specific local model (qwen2.5:3b) under a specific integration (OpenCode + MCP). These numbers should not be compared against official BFCL leaderboard scores, which use different models, different retrieval architectures, and different evaluation protocols. They serve as internal benchmarks for tracking MemoriX’s evolution over time. 100000 9. Threats to Validity and Limitations 9.1 Construct Validity Task success rate alone is insufficient to measure memory quality. An agent may retrieve correct information but fail to use it appropriately, or it may succeed at the task while ignoring retrieved memories entirely. We mitigate this by decomposing memory quality into separate metrics (Recall@k, MRR, false-memory rate) and by analyzing the BFCL-derived pipeline in stages (corpus → retrieval → answer). Nevertheless, the mapping between our operational measures and the theoretical construct of “memory quality” remains imperfect. 9.2 Internal Validity The primary internal threats are LLM output variability, provider errors, prompt or budget differences, order effects, agent fallback behavior, and contamination through persistent runtimes. Our controlled-pair design, explicit seeds, isolated runtimes, manifests, and retry policy mitigate these risks. The mandatory negative control on no_memory runs—verifying that no memory infrastructure is accessible—is essential for attribution. 9.3 External Validity All experiments use a single model (qwen2.5:3b), a single agent framework (OpenCode), and a single memory backend (Titan). Results may not generalize to larger models, different agent architectures, or alternative memory backends. The BFCL-derived tasks, while drawn from diverse domains, represent a limited sample of the space of possible agent-memory interactions. Community-derived protocols are explicitly described as local adaptations. We do not claim universal superiority across all agents or domains. 9.4 Conclusion Validity The A/B benchmark uses 32 seeds per family, providing reasonable statistical power for detecting large effects. However, families with zero variance (0% or 100% in both conditions) cannot be statistically compared. Confidence intervals and effect sizes should be interpreted cautiously, particularly for the 16 tied families where the model’s inherent capability (or lack thereof) dominates any memory effect. 9.5 Technical Limitations of MemoriX Hot Site-only retrieval improves control but means that useful unvalidated information in the Candidate Store will not be retrieved automatically. Topic Blocks are a logical layer dependent on metadata quality; poor tagging can degrade retrieval. Internal atomization (splitting memories into facts) increases slot consumption for fact-rich content, potentially triggering premature capacity expansion. Elastic expansion mitigates saturation risk but does not eliminate the underlying memory and latency costs of growing active state. Finally, the consolidation pipeline selects events for promotion but does not automatically validate them—a human or orchestrator agent must still perform validation, creating a bottleneck at scale. 100000 10. Conclusion We presented MemoriX, a controlled persistent memory system for LLM-based code agents that addresses inter-session continuity as a knowledge-governance problem . The architecture separates recent events (Short-Term Memory), durable history (Cold Site), memory proposals (Candidate Store), and actively retrievable knowledge (Titan Hot Site), with explicit admission control, logical forgetting, project/user isolation, and elastic capacity management. Integration with OpenCode through MCP maintains a clean runtime boundary, and the SDLC orchestration layer structures multi-agent development workflows. Our empirical evaluation—spanning 2,048 A/B runs, BFCL-derived retrieval campaigns, multi-agent tests, and capacity stress experiments—demonstrates: +28.0pp improvement in overall agent task pass rate with memory 12 of 32 task families significantly improved, with 7 families reaching 100% pass rate 76.8% retrieval accuracy on blind BFCL-derived curation at ×5 scale +12.5pp multi-agent task success with zero information leakage Safe saturation at 50,000 active items with no silent overwrites under 120× overload Four task families showed regression with memory, revealing opportunities for improvement in schema-aware invalidation, deduplication, and forgetting mechanisms. MemoriX demonstrates that persistent memory for agents is not merely a storage problem but a governance challenge—one that rewards architectural clarity, explicit state transitions, and defensive design. Future work will address the identified regressions, explore alternative neural memory backends, and scale evaluation to larger models and longer-running multi-session workflows.
